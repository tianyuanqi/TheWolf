- 分类/严重程度：真实缺陷，**P2**，阻断通过。来源：本轮原范围内反例；不是新增要求或偏好。
- 依据：任务书 §4.6/§4.9 及 A7 的前端超时、结果核对与失败恢复。保守核对必须保留，但核对后需要存在可恢复的用户路径。
- 位置：[App.tsx](../../apps/desktop/src/App.tsx) 固定版本第 138–154、191–209、270–280 行；核心判断为 `uncertainPost.current && status.job_id === previousJob.current`。
- 触发：已有 `idle/job_id=null` 或已完成旧任务；用户点击更新；POST 因连接失败/超时没有送达服务端；随后网络恢复，GET 正常返回原来的闲置/终态任务。
- 预期：先查询本地、避免重复抓取；对于未受理的请求提供可核实且有限的恢复方式，用户能够继续手动更新。已有运行任务和已提交任务仍应核对原任务。
- 实际：`uncertainPost` 保持为 true，旧 job_id 一直相同，因此忽略 GET 的闲置/终态；每次核对再等待 120 秒，然后重新显示“更新结果待核对”。`updateError` 继续禁用更新按钮，再次“核对结果”重复同一循环。在没有其他客户端创建新任务的情况下，本窗口无法恢复，需重新加载应用。
- 证据：运行固定源码真实 `App` 回调的[隔离探针](TASK-20261002-01-review-probes.cjs)，仅替代 React 调度、时钟和网络。两种初始状态各执行两次完整超时/核对周期，POST 始终 1 次、GET 增至 9 次；服务端分别维持 idle/null 与 completed/旧 ID，更新按钮仍禁用，核对按钮可点击。对照中让 GET 返回新 ID 的失败终态后，同一真实回调立即恢复按钮，定位到上述身份判定。
- 影响：一次请求未送达即可造成桌面更新入口持续不可用；已有行情和公告未损坏，未发现该路径自动重复采集。
