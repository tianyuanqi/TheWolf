## 2. 根因与最小修复

R01成立：POST连接失败后，不确定标记一直等待job_id变化；服务器仍idle或旧终态时，每次“核对结果”又开始120秒等待，永远无法恢复更新入口。旧验证覆盖新任务成功/失败和提交后丢失响应，没有覆盖请求根本未送达且旧任务不变的实际App回调，因而漏掉此分支。

改动仅在[App.tsx](../../apps/desktop/src/App.tsx)维护原请求开始时刻并复用120秒边界。首次不确定请求先只读轮询；等待截止后，人工“核对结果”成功返回相同旧idle/终态且任务未运行，结束本次等待并恢复手动入口，提示“未发现新的更新任务…”。核对仍只GET，新的POST必须由用户再次点击；提示不声称确定未受理或本次检查成功，旧完成消息不冒充本次结果。服务端单写者锁继续协调随后明确人工发起的请求，包括延迟受理的请求。

已发现新job_id时，继续跟踪该任务；运行中不解除等待，查询失败仍保守核对，新完成终态刷新固定切片。原成功检查时间由服务端返回，未发现新任务时不虚构新时间或刷新旧完成任务。API、Python、Rust、数据模型、来源、依赖和样式未改变，没有更改已确认契约。

新增[真实App回归](../../apps/desktop/scripts/update_recovery.test.cjs)，及README该入口说明；未改独立审查探针。该测试读取实际App.tsx，调用真实按钮/轮询/effect；仅替代React调度、时钟与网络，不镜像恢复算法。
