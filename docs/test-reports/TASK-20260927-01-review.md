## 3. 已证实缺陷

以下行号均属于待审提交；最小修复建议是交接建议，本次没有执行修复。所有问题交由原实现任务处理，审查者复核后关闭。

### R01 / P2 / 旧输入重试会将当前指针退回旧版本

- **位置：** `python/src/pmi/snapshot.py:360–367`。
- **触发：** 先发布 A，再发布修订 B，随后重放已归档、获取时间早于 B 的同一份 A，例如恢复后重试旧批次。
- **预期/实际：** 同一旧批次的重复导入应幂等，不能隐式撤销后来已发布的修订。实际 `INSERT OR IGNORE` 跳过已有 A，但随后的 upsert 无条件把 `current_snapshot` 改回 A。反例收盘价从 B 的 `10.60` 退回 A 的 `10.50`；数据库仍只有两份快照，因此只检查去重数量不能发现回退。
- **影响：** 默认页面和 `/api/slice` 静默显示旧行情；固定 B 仍在，原件未删除。新增公告后重试旧的单公告发布输入也有相同指针风险。当前 CLI 重放要求四份原件；单公告例针对存储接口，不能误称当前 CLI 可直接重放三份原件。
- **证据：** 附录 A 的顺序重放反例；`evidence/probes.log`。置信度高，已在隔离合成数据复现。
- **最小修复建议：** 区分“已发布批次重试”与“有依据的新观察/显式回退”。重复批次不自动推进当前指针；真实来源从 B 改回 A 的新观察需有明确版本/观察语义，不能用旧批次重放替代。
- **关闭条件：** A→B→旧 A 重试后当前仍为 B，旧 A/B 固定读取不变；同时验证最新批次重试和真正新修订，避免仅按内容去重误吞合法更正。

### R02 / P2 / 固定快照 ID 没有校验与清单内容身份的一致性

- **位置：** `python/src/pmi/snapshot.py:390–397`、`:415–418`。
- **触发：** 本地索引损坏或恢复拼接出错，使 A 行的 `manifest_object_id` 指向另一份完整的 B 清单；两份清单共享原始行情/PDF 对象，例如相同原件被不同标准化解释。
- **预期/实际：** 本实现的 `snapshot_id` 就是清单 SHA-256；请求 A 应返回 A 清单或明确拒绝。实际仅校验所选 B 对象自己的哈希及 raw/PDF 字段，未检查 `snapshot_id == manifest_object_id`。隔离 SQL 仅修改这一列后，请求 A 返回 `snapshot_id=A`，但收盘价为 B 的 `10.60`，没有错误。
- **影响与前提：** 固定引用可能被错误标为另一份金融事实。必须已有本地数据库映射错误；没有证明未授权网页能修改 SQLite，不把此反例描述为远程权限绕过。现存真实数据库两行的映射核对正确。
- **证据：** 附录 A 的单列损坏注入，`evidence/probes.log`。置信度高；属于固定身份/损坏隔离缺口，按有条件的 P2 处理。
- **最小修复建议：** 对现有契约校验请求 ID、数据库快照 ID、清单对象 ID 的对应关系；不符即拒绝。若未来引入不同身份算法，应通过显式契约版本处理。
- **关闭条件：** 本反例返回可识别的快照损坏错误；正常旧契约 3、新契约 4、当前及固定读取仍通过。

### R03 / P2 / 数据库故障越过 API 错误边界

- **位置：** `python/src/pmi/api.py:90–94`、`:104–108`、`:119–123`；调用 `snapshot.py:287–304`。
- **触发：** 数据根的 `slice.sqlite` 损坏，或 SQLite 抛出无法打开、锁定等数据库异常。本次实际注入的是错误数据库头，没有把其他异常情形写成已实测。
- **预期/实际：** 实现任务要求失败返回稳定错误码与可读消息。现有三个路由只捕获 `SnapshotError/OSError/ValueError`，不捕获 `sqlite3.Error`。错误数据库头实测产生未处理 `DatabaseError`，ASGI 响应为 `500` / `Internal Server Error`，不是结构化 `detail.code/message`。
- **影响：** 用户只能看到通用请求失败，无法分辨数据库损坏与其他错误；当前数据不会假成功，但恢复诊断契约未满足。此问题不代表读取绕过认证。
- **证据：** 附录 A 捕获实际 ASGI 已发送响应；`evidence/failures.log`。置信度高。
- **最小修复建议：** 在适当的存储/API 边界归一数据库异常，返回稳定、安全的错误码；保留内部诊断。不要通过重新建库、空数据或回退其他版本隐藏损坏。
- **关闭条件：** 损坏数据库及一个适用的不可访问/锁故障返回约定结构；正常、首次空库、对象损坏及旧固定读取不回归，真实资料不被重建覆盖。

### R04 / P2 / 桌面将创建子进程成功当作服务启动成功

- **位置：** `apps/desktop/src-tauri/src/main.rs:64–77`、`:86–93`；重试消费者 `apps/desktop/src/App.tsx:57–77`、`:117`。

- **最小修复建议：** 在有界时间内验证当前子进程存活及受保护的就绪响应，明确区分端口冲突和启动失败；提供有效的恢复路径并回收失败子进程。不要复用未知进程或取消 token 校验。

### Q01 / 潜在 P2 / 四份原件的实际获取时间能否准确重建

- **位置：** `sina_slice.py:264–275`、`snapshot.py:333–363`、`:415–419`；实现任务 §4、数据模型 §2 要求区分获取、首次见到及记录时刻。

- **下一步/关闭：** 原实现者提供逐原件时间与对象哈希的对应证据，明确批次 first_seen 的含义；如不能恢复应记录未知，并在今后获取中保存准确观察元数据。审查者复核同内容重取、追加公告及重放的时间含义。证据缺口置信度高；对现有研究结果的影响尚未证实，因此不列作已证实金融错误。

### 9.3 R01 剩余反例：合法新观察恢复旧内容无法成为当前版本

- **类别/严重性/置信度：** 已证实缺陷，P2，高。沿用 R01，不重编号隐藏原修复过程。
- **位置（c39ee17）：** `python/src/pmi/snapshot.py:361–369`；实际适配器的内容派生批次规则见 `python/src/pmi/sina_slice.py:189–196`。
- **触发：** 时刻 t1 来源为 A，t2 来源改为 B，t3 再次真实取得与 A 完全相同的内容（来源撤回 B、更正恢复原值等）。t3 是更晚的新观察，不是重试 t1。
- **预期：** t1 的旧输入重试不能撤回 B；但 t3 的真实新观察应可成为当前内容 A，同时保留 A/B 固定视图和观察证据。原报告 R01 已明确要求不能因内容去重吞掉合法更正。
- **实际：** `retrieved_at` 不参与清单内容身份。A 已存在，`INSERT OR IGNORE` 的 `inserted=False`，所以即便 t3 晚于 t2，`:369` 仍禁止推进指针。探针返回旧 A 的 ID，`/api/slice` 对应当前收盘价仍为 B 的 `10.60`，期待为 A 的 `10.50`。
- **实际调用链关联：** `build_payload()` 的 batch_id/source_version 来自原响应哈希及固定报告哈希。相同完整原件在 t3 恢复时不会自动产生新的观察批次 ID；新观察日志被追加，也没有被 `publish_snapshot` 用于当前指针语义。因此不能只用测试手工改 batch_id 来证明实际适配器已覆盖该情形。
- **影响与限制：** 一次合法撤回/回改后，默认视图可能继续显示被撤回的 B；原件和固定版本仍在。本次是隔离合成反例，未声称新浪真实归档已经出现过此种变更。
- **最小建议：** 明确区分不可变内容身份、一次观察/获取身份和当前指针的观察顺序；旧批次重试应幂等，更新的真实观察可引用已存在内容。不要通过每次重试都生成新内容版本规避问题，也不要改写旧 `first_seen_at`。
- **负责人/关闭条件：** 原实现任务修复；审查者复核 A→B→旧 A、A→B→较晚新 A、随后旧 B 重试、最新观察重试及不同内容 C，并沿实际适配器/CLI 验证观察身份，不只手工换 batch_id。
