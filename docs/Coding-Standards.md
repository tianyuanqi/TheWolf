# TheWolf 代码编写规范 V1

本规范适用于人工及 AI Agent 编写的 Python、TypeScript/React、Rust 代码。目标是可读、可维护、可测试、可追溯、不过度设计；能够运行不是唯一完成标准。

本文件是 [AGENTS.md](../AGENTS.md) 的代码编写细则。授权、交付、独立审查和恢复要求以该入口为准，当前范围与进展只在 [status.md](status.md) 维护。引用设计文档不代表批准其中全部提案、建议数值或未来模块。

新增及本轮修改代码按本规范执行；既有最小工程随相关任务逐步完善，不因采用规范启动全库重构。

## 1. 可读性优先

优先让维护者理解业务含义，不追求最少行数。避免把复杂业务压成一行、嵌套三元表达式、难以理解的链式调用、无意义缩写，或把不同职责塞入同一函数。

## 2. 注释

复杂金融计算、数据清洗、去重、来源选择、异常修正、时间区间和交易日处理，必须解释代码无法直接表达的业务依据、约束或选择原因。不要逐行复述代码。

外部金融数据必要的来源、字段定义、单位、时间口径、复权状态、原始或派生性质、版本及特殊规则，必须进入数据契约或元数据。无法确认的信息标注未知并限制依赖它的计算或历史用途，不能靠猜测补齐。已有统一定义时引用它，不在每处重复维护。

非直观实现须解释原因。临时方案使用 `TODO:`，已知未修复问题使用 `FIXME:`，说明具体原因和处理条件；影响当前交付的问题关联状态文件中的开放问题。未来功能想法不自动成为 TODO 或实施承诺。

## 3. 函数与模块

函数围绕单一清晰职责组织，上层函数可以编排获取、校验、标准化、保存等多个步骤。不要把流程编排本身误判为职责混杂。

函数超过约 50～80 行、嵌套超过三层、承担多个业务职责或需要大量阶段注释时，考虑拆分。这些只是提示，不是硬限制；不机械拆成大量一两行的函数。

## 4. 命名

名称表达业务含义，例如 `announcement_publish_time`、`total_market_cap`、`fetch_daily_market_data`。避免 `tmp1`、`data2`、`do_it` 等无法说明职责的名字；短小局部变量与框架约定按上下文判断，不按名字黑名单检查。

允许 `pe`、`pb`、`roe`、`eps`、`ttm`、`yoy`、`qoq` 等通用金融缩写，非通用缩写需解释。缩写不代替指标口径定义。

## 5. 类型与接口契约

Python 新增核心业务代码原则上使用类型标注。稳定复杂结构定义明确模型，不长期通过无约束 `dict` 或 `dict[str, Any]` 传递核心金融事实。

API 输入、输出及错误结构应明确，并在可信边界执行必要的运行时校验。TypeScript 类型声明或 `as` 断言不能代替外部数据校验；避免用宽泛类型掩盖契约不一致。契约复用或生成遵循现有项目机制，不为同一字段维护相互偏离的多套定义。

## 6. 金融单位、口径与精度

执行 [AGENTS.md 第十三节](../AGENTS.md#十三本项目专用约束)的金融口径要求。金额、股本、成交量、市值、比例、时间和价格均不能仅凭名称猜测含义；元/万元、股/手、小数/百分数、时区、复权方式及股本范围必须可查。

单位转换应集中在明确边界并可测试，不在不同模块隐式换算。每类数值按实际数据契约明确表示方式、精度、舍入规则，以及缺值、零分母、越界和非有限值的处理。按用途选择 Decimal、整数缩放或浮点数，不把 `float` 示例视为默认金融存储规范，也不强制所有计算使用 Decimal。

具体字段设计参考[数据模型](Data-Model-V0.1.md)，未确认部分随实际切片确认。

## 7. 原始数据、派生数据与版本

区分原始资料、标准化事实、派生计算与分析结果。已归档原件和已发布事实版本不得原地覆盖；清洗、修订和重新解析形成可追溯的新版本。原响应的保留期限遵循已确认的保存策略，不把所有临时响应都强制永久保存。

计算结果应关联固定输入、公式或算法版本和参数。引用与保留要求遵循 AGENTS.md 第十三节，不能只留下会变化的“最新数据”链接。

## 8. 缺失与异常数据

缺失、异常与真实零值必须可区分。禁止捕获异常后无说明地返回零、把 `None` 静默替换为零，或为使结果看起来正确而隐藏数据问题。修正必须有依据、记录和可追溯版本。

## 9. 异常处理

禁止裸 `except:`，优先捕获能够正确处理的明确异常。不能处理的错误向上传递；边界层确需捕获宽泛异常时，必须保留诊断信息并返回明确失败，不能伪装成功。

可恢复错误按明确策略重试或跳过，并记录状态；不可恢复错误及时失败。重试应有次数或时间边界，取消与资源清理不能被无意吞掉。

## 10. 日志

核心运行流程使用统一日志机制，不以调试 `print()` 代替正式日志。CLI 的正常结果输出、测试辅助输出可以使用相应输出方式。

记录有助于定位问题的证券标识、数据日期、来源、任务、错误类型、请求阶段和关联标识。不得记录密码、Token、API Secret、Cookie 等敏感凭据；异常文本、请求 URL 和载荷也须考虑凭据泄露。

## 11. 数据库与发布完整性

写入考虑唯一键、约束、幂等、事务、完整性及失败回滚。相同输入版本重复导入，不产生重复业务事实或重复发布；重试可以增加审计记录，内容更正必须保留新旧版本。不能为去重丢弃合法修订。

数据库事务不能单独保证数据库与文件系统的一致性。跨文件、索引和数据库的写入，必须保证查询不暴露半成品，中断后可恢复，重试不破坏已发布版本，既有引用仍可解析。发布协议参考[架构第十二节](Architecture-V0.1.md#12-原子发布恢复与完整性)，按当前切片落实必要约束，不提前建设全部存储模块。

## 12. 获取、存储与展示边界

网络获取与本地读取保持清晰边界，按获取、校验、标准化、保存、查询组织流程。断网不能阻止读取已保存的数据和公告。

前端负责展示与交互，核心金融规则由本地 Python 服务执行；不能只靠前端检查维护业务约束。Rust 桌面层负责相应生命周期和系统集成，启动、退出、进程与资源清理中的错误必须明确处理，不能无理由忽略。

## 13. 测试

金融计算、格式及单位转换、日期处理、清洗、去重、数据库写入、API 与公告解析原则上具有对应测试。以明确输入和独立可判断的预期结果验证业务行为，不能只是重复实现逻辑或追求覆盖率。

按风险覆盖正常路径、缺失与边界、失败及恢复。时间版本选择、来源修订、重复导入和发布中断须有适用的验证。测试使用隔离数据；真实接口、界面与恢复验证遵循 AGENTS.md 的验收和测试要求，Mock 或编译通过不能替代相应证据。

## 14. Bug 与回归

修复前判断是否可以用测试复现。对适合自动化复现的行为问题，先增加失败测试，再修复并确认通过。对不适合自动化的低风险或视觉问题，记录适用的复现与验证方式，不机械增加镜像实现的测试。

## 15. 重构边界

具体任务不夹带无关重构、大量改名、目录迁移、框架替换或技术升级。确有任务依赖时控制在必要范围；重大变化按 AGENTS.md 的授权规则处理。

## 16. 复用与抽象

相同业务逻辑稳定重复时考虑复用，不为第一次出现的简单逻辑设计多层包装。Factory、Manager、Provider、Adapter、Repository、Service 等名称本身不是问题；判断其是否解决实际职责、依赖或测试问题。已有清晰边界可以直接采用，不强制等到重复后才划分模块。

## 17. 第三方依赖

增加依赖前检查标准库及已有依赖是否足够、新依赖维护状况和实际维护成本。不得仅为几行简单功能引入大型依赖，不附带升级无关依赖。

## 18. 配置

凭据及机器专属路径不得硬编码到业务代码。服务地址、端口和数据目录集中管理，允许明确的开发默认值；运行时解析得到绝对路径是合理的，不要求所有路径均为相对路径。

配置与密钥管理遵循项目既有机制，真实私密配置不纳管。测试配置不得误指向用户真实数据目录。

## 19. Docstring

对外接口、核心业务函数、复杂计算、公共工具、数据模型及非直观算法，应按需要说明契约、参数含义、单位、返回值、重要异常及限制。简单且语义明显的私有辅助函数无需冗长 Docstring。

金融函数的说明须明确比例表示、有效输入及特殊值行为；不要用重复代码的文字充数。已有权威定义时引用，不复制易失同步的口径说明。

## 20. AI 代码规则

不得编造 API、数据库字段或已有接口，不猜测单位和金融口径，不为测试通过修改正确业务规则、删除有效失败测试或静默降低校验标准。

不确定时先读代码、模型和项目文档，再查证必要事实；不能查明且影响产品语义的问题才向用户澄清。AI 数据与外部文档的信任边界遵循 AGENTS.md 第十三节。

## 21. 实现选择与需求边界

已授权范围内的局部实现、测试和修复可以自主推进，不对常规内部步骤反复请求批准。产品范围、核心数据语义、数据源、保存策略、重大架构及已确认业务规则的变化，按 AGENTS.md 的授权规则处理，不能将建议自动当作批准。

## 22. 修改与交付说明

编码前明确任务边界并检查已有改动。交付应说明改了什么、原因、影响模块、是否改变数据库结构或引入依赖、验证结果及已知问题。未执行或受阻的验证如实标明；具体完成标准与 Git 操作授权引用 AGENTS.md，不另建审批流程。

## 23. 删除代码

删除前核实调用者、兼容性、暂时未使用的原因及已规划接口的约束。不能仅凭“似乎没用”大规模删除；未来规划也不自动要求保留无必要实现，按当前范围和实际依赖判断。

## 24. 格式化与静态检查

遵守对应语言已有 formatter、linter、type checker 及编译配置，不另建冲突规则。未配置的工具不宣称已检查通过；确需新增时按当前任务引入，不借规范采用一次扩建全部工具链。纯格式变更尽量不混入功能改动。

## 25. 交付前适用检查

按修改范围与风险检查：

1. 行为符合约定，必要的业务依据和注释可查。
2. 职责、命名和类型清楚，无明显无益重复或过度抽象。
3. 无裸异常捕获、静默失败、遗留调试日志、硬编码凭据及机器专属路径。
4. 金融来源、单位、精度、时间与版本明确，缺失不混同于零。
5. 受影响测试、类型检查及构建按需执行，结果与当前代码对应。
6. 涉及 UI 时检查真实界面；涉及数据发布与恢复时验证必要失败路径。
7. 依 AGENTS.md 完成适用的独立审查；自审不得写成独立审查通过。
8. 改动聚焦，必要文档及开放问题已更新。

文档和低风险非行为修改使用差异自检及适用工具检查，不机械重跑业务测试。清单通过不等于用户验收或发布完成。

## 26. 历史时间正确性

执行 AGENTS.md 第十三节的时间正确性要求：历史查询在计算、筛选与检索前选择当时可知版本；数据所属期间、发布时间、获取时间和修订版本不能混用。历史版本不足时返回明确限制，禁止静默以最新值替代。

具体时间字段与选择规则参考[数据模型](Data-Model-V0.1.md)，在已授权切片内确认并验证。模型中存在字段不能证明来源具备对应历史数据。

## 总体原则

正确性、数据可信度和可追溯性优先，再考虑可读性、可维护性、性能和代码简短程度。数据来源、处理过程与结果依据必须能够重新检查；不得以代码更短或更复杂为由削弱这些能力。
