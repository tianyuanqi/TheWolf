# TheWolf 独立代码审查规范 V1

制定日期：2026-10-09。依据用户对独立审查建议及项目适配方案的确认制定，适用于人工及不同工具、模型的 AI Agent。采用本规范不启动开发、创建审查会话或改变 Git 授权；实际任务安排与进展以 [status.md](status.md) 为准。

## 2. 风险分级与触发条件

L0–L3 是本项目自定义的审查深度，不是模型档位、窗口数量或厂商分工。每次改动均执行适用的 L0 检查，L1–L3 在此基础上增加要求。触发多项时取所需的最高等级并覆盖相关检查；不按行数或文件数量机械定级。

| 等级 | 适用范围 | 最低要求 |
|---|---|---|
| L0 基础检查 | 每次改动；文档及低风险非行为修改可止于此 | 差异自检、适用工具检查；文档按 V-DOC，不机械启动独审或业务测试 |
| L1 常规独审 | 局部功能、普通行为修复，未触发更高等级 | 独立检查全部本轮人工及AI编写的源码、测试、配置等差异、相关上下文及消费者，核对受影响测试；UI增加真实界面检查 |
| L2 深度独审 | 核心金融计算、时间版本选择、来源适配、发布与恢复逻辑、公共API或跨模块行为，未触发L3 | 增加关键反例、失败恢复、受影响实际消费者及真实接口/界面验证；按风险核对旧行为与兼容性 |
| L3 重大变更审查 | 重大架构或信任边界改变、破坏性接口、已有数据迁移或保留/删除策略重大改变 | 实施前独立方案审查，通过后实施；完成后独立代码审查及受影响行为回归，必要时验证数据恢复 |

是否可止于L0按实际影响判断，不以“未改业务源码”为依据。测试断言、跳过规则、验证脚本、构建配置、依赖及安全配置的改动，只要改变运行行为、验证覆盖或质量门槛，最低为L1；触及上述L2/L3条件时取更高等级。确实不改变这些行为或门槛的文档、注释、排版等仍可按L0处理。

规划者结合 Task-Workflow 的复杂度、错误影响、不确定性与可验证程度，说明等级、触发原因、重点和适用验证。任务书保存约定，status保存实际安排；简单任务可简写。开发者不得自行免除独审或降低等级。实际范围或关键假设变化时重新评估，重要范围与质量门槛的变更由用户决定。

既定独立审查者在首审及复审时，须对照实际差异、受影响路径与最低等级触发条件复核定级，不直接沿用规划者标签；发现低估时记录依据并按所需等级补齐检查，必要材料或独立性条件不足则保留阻塞。已实施内容若原本应触发L3而未做方案独审，须记录此前置缺口、暂停依赖它的后续实施并补审固定方案，再审对应代码，不能把事后补审写成实施前已通过。此核对由既定审查者完成，不增加审批角色或自行扩大业务授权；需改变已确认安排或用户决定时交回具体影响，版本适用按下述规则处理。

普通函数拆分、局部命名或既有边界内的适配，不因被称为“重构”自动成为L3。纯文档编辑若改变需求、权限或数据策略，须先明确相应决定；文档检查本身不能证明未来代码已满足新要求。

工程规则的版本记录、执行中更新的影响评估与用户决策边界统一按 [Task-Workflow §4.1](Task-Workflow.md#41-阅读顺序与信息归属)执行。尚未实施任务应在开始前补齐适用安排；正在实施任务发现需补审时明确受影响部分和材料，保留原有效证据，不重启无关工作。

## 3. 独立性与会话安排

1. 代码审查者未参与本轮实现；方案审查者未参与所审核心方案的制定。均须使用独立上下文，自行读取已确认需求、适用规则、固定材料与相关源码。不得fork完整开发历史冒充独立上下文。
2. 开发者摘要和解释只是线索。审查者先依据需求、差异和调用关系建立判断，再核对解释与证据；可以检查方案是否有误，但不能自行新增业务要求。
3. 同厂商、同模型可以审查；换模型或提高推理档位不证明独立。实际审查者、工具、方式及可取得的配置如实记录，未知不虚构。
4. 会话复用、可见窗口或子Agent渠道按本任务已确认安排执行，与等级分开记录。已选择可见窗口时不得用后台子Agent替代；缺少必要独审时保留待审，不以自检代替。
5. 同一审查者可先审方案、后审代码及复审；提出发现、关闭条件或可选处理思路不等于承担实现。审查者若直接制定受审核心方案或修改业务实现，须另安排独立审查者检查其参与部分，不能自行放行。

## 4. 方案审查与固定材料

L3方案审查聚焦本轮系统边界、职责与依赖、接口和数据契约、实际消费者、信任边界、迁移与恢复、验证可行性及关键未知。只要求足够支持本轮实施，不提前设计完整平台。

方案材料须关联任务ID、已确认需求、真实代码基线SHA及相关已有增量，并固定方案/契约等材料版本，可用准确文件清单与SHA-256核对。不能虚构尚未产生的待审代码提交；实现尚未开始和实现测试尚未执行，本身不是方案审查材料缺失。关键技术路径未验证时明确所需的有边界最小验证及授权，不能把假设写成已验证事实。

方案结论按第8节记录，通过仅允许进入已获授权的实施阶段，不代表代码通过或用户验收。阻断方案问题解决前不实施依赖它的部分。自动模式下，生成任务书及安排后仍须本人确认开发，再按其中安排进行方案审查和实施；若用户只授权方案审查，审查通过后仍不启动开发。

代码审查前按 [Task-Workflow §7](Task-Workflow.md#7-开发与修复的固定交付)核对待审条件与材料。提交策略使用真实完整SHA；固定快照策略按 [§7.2](Task-Workflow.md#72-自动任务书模式固定快照审查与git待提交)核对基线、清单、文件模式、差异和必要未跟踪文件。材料须包含任务约定、影响范围、验证结果与失败记录、恢复结果及已知限制。

读取最新规则并按Task-Workflow §4.1判断适用版本，不将变化中的工作区源码混入固定版本。方案及代码审查的入口核对若发现关键版本/材料缺失或不匹配，按 [Task-Workflow §9.2](Task-Workflow.md#92-可复制的审查与修复指令)报告交审前阻塞；带缺口有限预审同样按该节处理。通过入口核对、开始正式审查后才发现关键证据不足的，按本规范第8节判定。

## 5. 实质审查检查表

首轮应集中检查约定范围，覆盖本轮全部人工及AI编写的源码、测试、配置等差异，并按需追踪上下游；机械生成文件或大型静态数据说明检查方式，不能把AI编写代码当作生成文件豁免。局部审查必须声明范围，不能把未审部分当作已通过。下表按实际影响选取，不适用项说明原因。

| 检查方面 | 必须核对的内容与证据 |
|---|---|
| 需求与范围 | 已确认目标、验收与实现一致；无漏项、未经授权功能、无关重构或依赖升级；方案问题同样可提出 |
| 正确性与边界 | 正常输入、空/缺失/异常、区间首末、精度及错误状态；预期来自需求或独立可判断规则，不能仅复述实现 |
| 接口与消费者 | 输入/输出/错误及运行时校验，兼容性与调用链；公共改动验证实际消费者，不以双方各自Mock通过替代联调 |
| 状态与恢复 | 重复操作、并发/晚返回、取消、启动/退出、中断、重试与结果不确定；核对幂等、旧版本、资源归属及恢复状态 |
| 安全与数据边界 | 本机可信服务执行必要校验，路径/外链/网络与写权限符合约定；凭据和私密信息不泄露，测试不指向正式数据 |
| 架构与兼容 | 职责、依赖方向及本轮系统边界符合已确认架构；重构与旧系统应保留的实际行为比较，明确获准变化，不仅检查新代码能运行 |
| 可维护性与规范 | 职责、命名、类型、中文注释及文档契约按代码规范检查；无无益抽象、静默失败或硬编码私密配置，不用个人偏好强制返工 |
| 测试与证据 | 检查断言有效性、独立预期、关键反例及失败路径；代码出错时检查能否发现，Mock是否绕过关键边界；关联被测版本、输入、环境、命令与结果 |
| 真实界面与使用 | 核对受影响页面、公共组件消费者、加载/空/错误/成功、长文本、窄窗口、键盘与焦点；截图/实际操作证据不由构建替代 |
| 文档与交付 | 行为、配置、契约、README与实现一致；所审版本及补充材料可重建，未执行与未核实准确披露，环境恢复有读回证据 |

验证选择及实际命令以 [Task-Workflow §10](Task-Workflow.md#10-稳定验证入口与证据)和README为准。复用仍有效且未受影响的证据；独审可针对关键路径运行检查或构造探针，不无理由重复全量测试。测试退出码、断言和业务结果交叉核对，测试数量、编译成功或“未发现明显Bug”不能单独证明通过。

以下检查落实AGENTS第十三节及相应权威文档，只覆盖本轮已确认能力，不因概念模型存在就要求实现全部schema。

| 本地运行 | 按本机单用户及回环产品边界检查实际访问、Host/Origin、服务身份、接口版本、进程所有权与写开关；需求取消凭证后按新契约验证，不擅自加入账号/云服务或保留旧鉴权断言 |

## 6. 发现、严重程度与阻断判断

“问题类型”“严重程度”“是否阻断”分别记录。问题类型及处置沿用 [Task-Workflow §8.1](Task-Workflow.md#81-审查责任和发现分类)的真实缺陷、必要验证缺失、有依据未证实疑点、非阻断建议、范围外事项。疑点先有限查证，不能自动进入改码队列；工具告警须核实。

对已证实缺陷按实际触发条件、影响范围与恢复代价定级；风险不夸大，不按模型置信度定级。

| 等级 | 影响说明 |
|---|---|
| P0 致命 | 严重不可恢复数据/研究依据破坏，重大敏感信息泄露或系统级失效 |
| P1 严重 | 关键业务失效，重要金融或历史结果错误，边界绕过或大范围回归 |
| P2 一般 | 局部功能/边界/兼容性缺陷，或有具体证据的维护问题影响适用要求 |
| P3 轻微 | 影响较小的已证实缺陷或强制规范违规；仍需检查是否违反本轮要求 |

严重程度不构成自动放行依据。违反当前已确认要求或适用强制规范的真实缺陷，以及关键验收所需的验证缺口，均阻断通过；P2/P3不因级别低而自动延期。纯改进建议的缺陷等级可记“不适用”，明确非阻断；疑点与补证项记录潜在影响或暂定等级及未证实部分，不伪装为已证实缺陷。

每项发现须可核实，至少包括：稳定ID、所审阶段与版本、类型、严重程度、是否阻断及理由、准确文件/代码或资料位置、约定依据、触发条件、预期与实际、证据、影响、负责人及可判断的关闭条件。报告可给修复思路，但不要求审查者替开发者设计唯一补丁。清楚的静态代码路径可以证明问题，不强制每项运行复现；未知必须写明所缺证据。

不得覆盖或删除历史发现与结论。开发者可登记“已修复并自测”或提交反证；“已独立验证”的结论须有审查者核对关闭条件的依据。协调者据此同步status，报告保留该轮关闭/保留/重开/新增及理由。“已驳回”须有反证和处置依据，不等于删掉原发现。

用户明确决定延期、风险接受或调整范围时，记录授权、原条件未满足事实、影响、剩余限制、责任及后续条件；不得将未修复缺陷记为已验证关闭，或把原验收要求写成已全部满足。此类决定不能由开发/审查Agent自行作出；原约定未改变时仍按阻断处理。

## 7. 修复、复审与有限往返

执行 [Task-Workflow §8.2–§8.4](Task-Workflow.md#82-修复前后必须核对的内容)：先核实根因与反证，再做最小必要修复；适合自动复现的缺陷尽量证明修复前失败、修复后通过，并检查相邻边界、旧关闭项的受影响路径及实际消费者。不删除有效测试、放宽断言或牺牲另一项约定。

方案和代码两阶段首轮分别标识；实质方案修订、补证和代码修复送回复审共享本任务的有限次数，不因进入代码阶段清零。具体计数与默认停止上限只在Task-Workflow §8.4维护，实际计数只在status维护。触发停止条件后按该节交回诊断；停止不能解释为通过，也不自动回滚或删除数据。

复审核对上轮到本轮的全部新增差异、原关闭条件、受影响调用者/数据/恢复路径及相对初始基线的累计范围。已关闭且未受影响的事项沿用有效证据；重开须给新证据、相关改动或原证据失效理由。新问题注明修复回归、原范围漏查、新需求/偏好或约定冲突，不借复审扩大范围。

## 8. 结论与通过条件

本节用于已经开始的正式审查；交审前阻塞和另获授权的有限预审见第4节及Task-Workflow §9.2，不套用正式结论。正式结论沿用“通过 / 需要修改 / 关键材料不足无法完成判断”；同时注明方案/代码阶段、所审版本和覆盖范围。“基本通过”“有条件通过”不能掩盖关键未知。发现已确认阻断缺陷时记录需要修改，并同时披露材料不足；尚无已确认阻断缺陷，但审查中发现关键依据不足导致无法判断时，结论为“关键材料不足无法完成判断”，明确缺口并保留已有发现及有效证据。

正式通过须同时满足：

1. 该阶段约定范围符合适用要求，必要检查及关键验收证据充分；无未关闭阻断缺陷或影响关键判断的未知。
2. 适用测试、实际消费者和必要界面/恢复检查有对应版本的有效证据；不适用/未覆盖能力及非阻断建议明确保留。
3. 材料完整、固定版本和被测内容一致，补充材料单列可核对；报告真实反映审查者、范围、实际检查、未执行原因及问题处置。
4. 本轮测试临时影响按基线恢复并实际核验；影响正常使用、数据安全或证据可信度的未恢复项已解除，用户明确保留的环境准确交接。

方案通过不代替代码审查；代码通过不代替用户验收、Git提交或发布。代码最终收尾按 [Task-Workflow §9.3](Task-Workflow.md#93-通过与归档)核对工作区与所审版本，固定快照任务继续停在“独立审查通过，Git待提交”。相关业务差异出现时重新验证并审查，不把旧批准沿用到新内容。

## 9. 权限、报告与规则落地

审查源码默认只读，所有阶段均不得直接修改原工作区业务代码或有效测试；允许在隔离副本中构造探针、运行获准检查、写入指定报告/证据。复审权限不因发现缺陷自动扩大。原真实库操作、来源请求、依赖安装、费用、消息发送、提交/合并/发布仍按AGENTS和本任务明确授权执行。

按 [Task-Workflow §10.3](Task-Workflow.md#103-测试结束后的配置与状态恢复)记录基线并恢复，成功、失败和中断均适用。只有实际权限配置才可称为技术只读隔离；共享同权限工作区中的禁改规则须如实称为操作约束，不虚构技术保护。

报告沿用Task-Workflow §8.1固定字段，在其中补明审查等级与理由、方案/代码阶段、实际独立性及适用规则版本。规则与任务材料可用真实提交或文件指纹单列版本。默认报告路径及跨会话入口沿用 [§9.2](Task-Workflow.md#92-可复制的审查与修复指令)，正式方案独审及另获授权的有限预审均在同一任务报告中注明阶段/性质追加，不能覆盖旧结论。当前状态由指定维护者串行更新；其他参与者交回待同步事项。

机械检查优先复用README已有入口；重复且可确定判断的问题在后续获准任务中转为测试/静态检查，有误报的规则用触发、有效反例和无关改动验证后收窄。规则说明不证明脚本、CI、分支保护、只读权限或自动派发已配置。以后明确PR/合并流程时再接入适用CI与分支保护；本地固定快照仍须核对材料、证据和最终版本。采用本规范不自动授权建设这些工具。
